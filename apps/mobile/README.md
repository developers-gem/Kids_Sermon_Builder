# Kids Sermon Builder — Flutter mobile app

Consumes the exact same REST API as `apps/web` — no separate backend logic,
no direct MongoDB access, matching the project's core architectural rule.

## Important: verification status

**This code has not been compiled, `flutter analyze`'d, or run.** The
sandbox this was written in has no Flutter/Dart SDK installed and no
network access to pub.dev or Flutter's download servers, so none of the
usual checks that were run on the TypeScript backend/web app (`build`,
`lint`, live HTTP request tests) were possible here. Every other part of
this monorepo was verified that way; this one wasn't, and that's a real
difference in confidence level, not a formality.

What *was* done to reduce risk despite that:
- The REST API contract is followed exactly — types, endpoints, and request/
  response shapes were copied field-for-field from the server code and the
  web client that already talk to this same backend successfully.
- Two Flutter API choices that looked plausible but weren't verifiable were
  deliberately walked back to older, long-stable APIs instead of newer ones
  that might not exist in whatever Flutter version this actually builds
  against: `Color.withOpacity()` instead of the Flutter 3.27+
  `withValues(alpha:)`, and `DropdownButtonFormField`'s `value:` instead of
  a newer `initialValue:` parameter.
- The color palette is not eyeballed — it's the actual web app's `oklch()`
  design tokens run through the real OKLab→linear-sRGB matrix transform
  (see the git history / conversation this was built in), not approximated
  hex guesses.

**Before treating this as working software:** run `flutter create .` in
this directory to generate the missing `android/`, `ios/`, and other
platform runner folders (a real Flutter project needs these; they're
normally autogenerated by the Flutter CLI and version-matched to your
toolchain, so hand-writing them here would be lower-confidence busywork
than just running the command), then `flutter pub get`, then
`flutter analyze` and fix whatever it finds — some issues are likely, this
is real, hand-written code that has never been machine-checked.

## What's built

- **Auth**: register/login/logout, silent session restore on launch. Real
  attention was paid to a genuine cross-platform gap: the backend issues
  refresh tokens as an `httpOnly` cookie, which only means something to an
  actual browser. `ApiClient` captures the `Set-Cookie` header manually on
  login, stores the value in `flutter_secure_storage`, and replays it as a
  `Cookie` header on `/auth/refresh` — httpOnly blocks `document.cookie` in
  JavaScript, not a raw HTTP client reading the header, so this is doing by
  hand what a browser does automatically, not bypassing anything.
- **Story library**: browse and search the 6 built-in stories; tapping one
  creates a lesson from it via the same `POST /api/lessons` the web
  Builder uses, then opens it.
- **Custom AI story builder**: passage/age-group/focus/illustration-style
  form → `POST /api/ai/generate-lesson`.
- **Lesson screen**: renders every active module (story, memory verse,
  games, object lesson, coloring page, closing prayer) via a shared
  `LessonContent` widget; narration playback per section through
  `audioplayers`, hitting the same cached-audio endpoint the web app uses;
  favorite/archive/delete/duplicate/share-link/download-PDF, all gated to
  actual ownership the same way the web app gates its buttons; "Generate
  coloring page."
- **My Lessons**: All/Favorites/Archived tabs, same as the web app.
- Visual identity matches the web app: same color tokens, same rounded
  "paper card" shapes, same warm/friendly tone.

## What's explicitly not built (be aware before assuming parity with web)

- **Lesson editing, version history, and regenerate-module** — the web
  app's Lesson Editor (Prompt 14) has no mobile equivalent yet. The lesson
  screen is view/listen/organize only.
- **Admin CMS** — no mobile screens for managing the built-in stories.
  Prompt 16's own screen list doesn't call for this on mobile either.
- **Offline support / network resilience** (Prompt 25) — no caching layer,
  no queued actions, no "offline mode." A dropped connection just shows
  whatever error the API call throws.
- **A real "share" destination** — `_share()` in `lesson_screen.dart`
  builds a link against a placeholder domain
  (`kidssermonbuilder.app`) since this mobile build has no shared config
  with wherever the web app actually gets deployed. Replace that with the
  real origin before shipping.
- Accessibility and performance passes (Prompts 24/26) — not done as a
  deliberate sweep here, the same as the web app's current state.

## Configuration

The API base URL is not hardcoded — pass it at build/run time:

```bash
flutter run --dart-define=API_BASE_URL=http://localhost:4000/api
flutter build apk --dart-define=API_BASE_URL=https://your-deployed-api.example.com/api
```
